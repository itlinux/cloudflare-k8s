= Steps to deploy Cloudflare on Kubernetes

Run a Cloudflare Tunnel from inside the cluster so Services are reachable on a
public hostname without exposing any public IP on the cluster.

== Prerequisites

* A running Kubernetes cluster with `kubectl` access.
* `cloudflared` on the machine you run the CLI steps from (see Install below).
* A domain managed in your Cloudflare account (this guide uses `k8s.itlinux.cc`).

== Install cloudflared

Debian / Ubuntu (apt). The repo path must end in `/cloudflared` — a bare
`https://pkg.cloudflare.com/ <codename> main` line 404s on the Release file:

----
sudo mkdir -p --mode=0755 /usr/share/keyrings
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg \
  | sudo tee /usr/share/keyrings/cloudflare-main.gpg >/dev/null
echo "deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared $(lsb_release -cs) main" \
  | sudo tee /etc/apt/sources.list.d/cloudflared.list
sudo apt-get update && sudo apt-get install -y cloudflared
----

RHEL / CentOS / Rocky (dnf):

----
sudo dnf config-manager --add-repo https://pkg.cloudflare.com/cloudflared.repo
sudo dnf install -y cloudflared
----

Verify:

----
cloudflared --version
----

== 1. Authenticate cloudflared

Opens a browser; pick the zone for your hostname (e.g. `itlinux.cc`).

----
cloudflared login
----

== 2. Create the tunnel

----
cloudflared tunnel create k8s
----

Check it:

----
cloudflared tunnel list
----

Example output:

----
$ cloudflared tunnel list
071d2411-9f29-4f6e-94d6-c0ca1179587c k8s  2026-01-27T18:55:06Z 1xlax08, 1xlax10, 2xslc01
----

== 3. Route the hostname to the tunnel (DNS)

This creates the proxied CNAME `<hostname>` -> `<tunnel-id>.cfargotunnel.com`
in Cloudflare DNS. Without it the hostname will not resolve to the tunnel.

----
cloudflared tunnel route dns k8s k8s.itlinux.cc
----

Verify (returns Cloudflare proxy IPs, not the cfargotunnel target):

----
dig +short k8s.itlinux.cc
----

== 4. Create the Kubernetes secret

The manifest mounts the secret expecting the key `credentials.json`, so keep
that exact key name. Substitute your own tunnel ID.

----
kubectl create secret generic cloudflared-credentials \
  --from-file=credentials.json="$HOME/.cloudflared/<tunnel-id>.json"
----

Check it (the data key must be `credentials.json`):

----
kubectl get secret cloudflared-credentials -o jsonpath='{.data}'; echo
----

NOTE: The `credentials.json` value is the tunnel secret. Never commit it to a
public repo. If it is ever exposed, delete and recreate the tunnel.

== 5. Make sure the origin Service exists

The ConfigMap in `cloudflared.yml` routes the hostname to a backend Service:

----
ingress:
- hostname: "k8s.itlinux.cc"
  service: http://front.default.svc.cluster.local:80
- service: http_status:404
----

Edit the `hostname` and `service` lines to match your real Service, namespace
and port. The target Service must already exist, or cloudflared returns
`no such host` / 502 even though the tunnel itself is healthy.

Quick throwaway backend for testing (creates a `front` Service on port 80):

----
kubectl create deployment front --image=nginx
kubectl expose deployment front --port=80
----

== 6. Apply the manifest

----
kubectl apply -f cloudflared.yml
----

Check the pod:

----
kubectl get pod -l app=cloudflared
----

Check the logs — look for `Registered tunnel connection`:

----
kubectl logs -l app=cloudflared --tail=20
----

== 7. Test end to end

----
curl -I https://k8s.itlinux.cc
----

`HTTP/2 200` means tunnel + DNS + ingress + origin are all wired correctly.

== Troubleshooting

Tunnel shows "down" / one connection flaps with `control stream encountered a
failure` and `datagram handler ... context canceled`: usually QUIC datagrams
hitting a reduced MTU on an overlay CNI (e.g. Calico VXLAN/IPIP). Force the
HTTP/2 transport by adding `protocol: http2` to the ConfigMap `config.yaml`,
then `kubectl rollout restart deploy/cloudflared`.

`no such host` for the origin: the backend Service named in the ingress does
not exist in that namespace (see step 5).
